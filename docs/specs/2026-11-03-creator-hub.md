# tracepost：本地多平台创作者数据看板与 Agent 接口

> 状态：项目骨架已建立（数据契约、共用查询、Web / CLI / MCP、合成 demo）；尚未接入任何平台账号。原暂用名 Creator Hub，因同名项目已存在改名 tracepost，本仓库是本规格的唯一 owner。
> 下一步：见 [v0.1 计划](../plans/2026-11-03-v0.1.md)，先验证「本人账号 → 一篇内容 → 本地快照 → 查询」的最小闭环；第一期交付仍须覆盖两平台、看板与 Agent 接口。
> 架构与来源复核见 [2026-11-03 架构研究](../research/2026-11-03-creator-hub-architecture.md)。本文负责需求，研究文档负责证据与选型理由。

## 1. 来源与已确认方向

来源是作者 2026-11-03 关于「小红书与抖音数据接入方案」的需求讨论及同日的架构复核；原始记录在作者私有工作区，不随本仓库公开。

用户已明确的方向：

1. 希望尽量自动化，不把日常手动导出、抄数作为主流程。
2. 倾向自行开发一个统一 Hub，新增平台时不再重复搭一套流程。
3. 项目独立于作者的私有内容运营台账，作为 GitHub 开源小项目持续迭代；该台账是首个实际使用者。
4. 先汇总需求、调研与实现交接，开发交给后续 AI / 独立项目。
5. 后续可扩展读评论、辅助回复等能力；这是产品方向，**不是现在执行评论、回复或发布的授权**。

同日架构复核中，用户进一步确认：

6. **第一期必须同时支持抖音、小红书**；单平台切片只是实施顺序，不代表首版范围缩成单平台。
7. **本地 Web 看板 + Agent 接口**均进入首版。作品基础指标、平台可提供的后台深度指标、快照趋势、账号粉丝趋势、同内容跨平台比较均需要；评论读取是 nice to have，不阻塞首版。
8. **GitHub public 源码 + 使用者各自在本机运行**，Windows 优先、跨平台设计；不是公开账号数据，也不是首版搭建在线 SaaS。
9. 以 GitHub 展示和社区采用为目标之一，许可方向选 **MIT**；可复用兼容代码，**不直接引入 AGPL 实现**，不能把 public 仓库等同于获得复用许可。

下文的数据契约与技术组合仍是实现建议，不冒充已安装或实测。看板、两平台、Agent 可用和 MIT 方向已经确认；具体依赖、账号授权与发布操作尚未批准。

## 2. 产品目标

把本人有权访问的创作者后台数据，经过采集、保留口径、快照存储，统一提供给人和 AI Agent。

需要能回答：

- 某一篇内容现在有多少曝光、观看、互动、涨粉？数据来自什么时候、哪个页面？
- 同一内容在两个平台分别表现如何？哪些数字不能直接比较？
- 发布约 24h / 7d 时的表现，以及之后的增长，是否有真实快照支持？
- 哪些内容持续增长、值得复盘？缺失字段是平台没给、登录失效，还是采集失败？
- 后续能否读取评论、辅助整理问题与回复草稿？

自动化成功不等于抓到了一个数字：数据必须可追溯，旧数据、缺失数据与失败必须看得出来。

## 3. 路线取舍

| 路线 | 本方案的定位 | 约束 |
| --- | --- | --- |
| 平台正式开放 API | 实现前先查资格、权限、字段和适用账号；可用时优先 | 当前没有核实个人账号能否获得所需权限，不能宣称两平台都没有 API |
| 专用浏览器触发后台自带导出 | 当文件覆盖所需字段时，作为浏览器采集候选 | 与“每天人工导出”不同；按钮、文件日期、字段与覆盖范围需实测，不假定两平台都有完整导出 |
| 本人登录的专用浏览器，读取页面产生的响应 / DOM | 自动化保底路线；优先结构化响应，DOM 补充或兜底 | 只读本人可见数据；仅抽查参考源码，未完成审查和账号实测；平台条款与风控风险仍存在 |
| 人工导出文件后导入 | 备用输入方式，也可用于人工核对采集结果 | 不把它当作满足“尽量自动化”的最终主流程 |
| 直接提取 cookie，脱离页面调用未公开接口 | 不作为默认实现 | 不绕过权限、签名、验证码或风控；如需改变路线，先重新评估与确认 |
| 第三方付费分析平台 | 原对话提及的备选，不是本轮选择 | 需要另外核实数据覆盖、授权、导出与费用，不预先购买 |

自研的是统一产品边界和数据链路，不意味着每个采集器从零重写。先审查可复用实现，比较直接复用、薄封装与自行实现的维护成本，再选择具体依赖。

不同平台可以采用不同路径，不要求“一律官方 API”或“一律爬页面”。降级必须记录实际来源与覆盖变化；遇到权限拒绝、验证码或风控应停止，不能把更换采集方式当作绕过限制。

## 4. 范围与阶段

### 第一切片：一个平台、一篇内容

- 人工完成一次授权登录；凭据留在专用本地状态目录。
- 读取一篇真实内容的标识、发布时间和若干可见指标。
- 保存一个有采集时间、来源和缺失原因的快照。
- 查询 / 导出 JSON，并与后台人工比对。
- 登录失效、页面改变或风控时明确停止；已有快照仍可查询。

先证明真实访问和数据口径，再定框架、看板与调度。失败时不要用模拟数据宣称端到端完成。

### 已确认 v0.1：两平台本地看板与 Agent 数据闭环

- 小红书、抖音的本人作品列表、单篇基础指标及可获得的后台深度指标。
- 一个账号每个平台起步；统一内容标识、快照与查询。
- 本地 Web 看板：作品列表、单篇详情 / 趋势、账号粉丝趋势、同步状态与字段覆盖；明确空数据、陈旧、部分成功与登录失效状态。
- 同一内容跨平台显式关联与并排比较；保留各平台定义和实际观测时间，不生成误导性的统一“播放总分”。
- 账号粉丝总量快照与相邻观测净变化；平台给出的新增 / 流失与自行计算的净变化分开。
- 本地持久存储；CLI 的机器可读 JSON 和 CSV 导出。
- 供 APX / 其他 Agent 使用的 MCP 查询能力；同步能力与纯查询区分。
- 登录状态、上次成功同步、字段覆盖和失败原因可检查。
- 定时采集作为手动同步验收后的增强，默认不启用。
- 公开交付提供无需账号和模型密钥即可查看的合成数据 demo、安装说明与能力矩阵；demo 明示为示例，不能作为真实采集验收证据。

### 非阻塞增强 / 后续候选

- 评论读取可在两平台核心闭环之后试验，不要求首版成功读取全部评论；问题归类、回复草稿后续再议，对外回复另设逐条确认。
- 长尾诊断、自动复盘辅助与更复杂的分析。
- B 站、视频号、快手、X、YouTube 等平台适配。
- 可选外部表格同步、内容归档、多账号。

### 非目标

- 首版不做发布、评论、私信、删除或其他平台写操作。
- 不做云端账号托管、账号矩阵、数据转售、验证码绕过或签名逆向。
- 不以“只读、低频、本人账号”为由承诺无封号风险。
- 不搭多租户 SaaS、桌面壳或复杂插件框架来证明一个采集链路。
- 不把 APX 作为 Hub 的运行前提；它只是 MCP / CLI 消费者之一。

## 5. 最小数据契约

先定义不变量，再选择数据库结构；不预先强制“宽表”或“长表”。

| 对象 | 最少需要保留的信息 |
| --- | --- |
| account | `platform`、稳定 `account_id`、展示名；不能只以昵称识别账号 |
| content | `platform`、`account_id`、平台原生 `content_id`、类型、标题、链接、发布时间 |
| content_group | 用户确认的跨平台内容关联；保留平台作品各自的 ID，不合并原始快照 |
| snapshot | 内容或账号引用、`collected_at`、平台统计时点 / 区间、时区、来源、`sync_run_id` |
| metric | 平台原字段、统一名、数值或 `null`、单位、统计口径、缺失原因 |
| sync_run | 起止时间、平台、采集范围、状态、成功/失败项、警告；失败不覆盖上次成功状态 |

要求：

- 内容以平台和原生 ID 识别；同题跨平台内容通过显式关联分组，不能仅凭标题自动合并。
- 来源返回的应用级 / 加密 ID 需带 `id_namespace`；不能假定开放 API 的 ID 与网页 ID 相同，跨来源关联须有可验证映射。
- 区分累计值、某日值和时间区间值。采集时间不等于平台数据更新时间。
- 每次同步记录请求范围、实际覆盖与是否完整；分页超时或接口失败不等于空账号，未采到作品不等于作品被删除。
- 缺失使用 `null` 和原因，例如 `not_exposed`、`login_required`、`parse_error`；真实的 0 必须保留。
- 每次新的观测保留快照；同一次同步重试不得重复写入同一观测，失败不得删除历史快照。
- 原始证据仅按必要范围脱敏留本地；禁止保存认证头、cookie 或整份未脱敏网络日志。
- 评论未来按需最小化存储，不默认把评论者信息、私信或原始账号数据放进公开示例。

### 指标口径

| 候选统一名 | 含义 | 限制 |
| --- | --- | --- |
| `impressions` | 曝光次数 | 没有就缺失，不能用播放代替 |
| `views` | 平台定义的观看 / 阅读 / 播放 | 保留原始定义，不能暗示各平台计数规则相同 |
| `likes` / `saves` / `comments` / `shares` | 对应互动计数 | 列表与详情可能不同步，需要来源和时间 |
| `follows` | 平台提供的归因涨粉 | 不用账号净增粉自动归因给单篇内容 |
| `followers_total` | 账号粉丝总量 | 与单篇归因涨粉是不同指标 |
| `ctr` | 平台定义的点击率 | 保留分母，不与其他“点击率”强行合并 |
| `avg_watch_time` | 平均观看时长 | 单位明确；不能当成完播率 |
| `completion_rate` | 平台提供的完播率 | 不是观看时长；图文或未提供时留空 |
| `skip_rate_2s` | 平台提供的 2s 划走率 | 可用性与适用内容类型待实测 |

百分比在内部采用统一数值尺度并标明单位，导出时显式转换。派生互动率标出分子、分母与样本区间；分母缺失或为 0 时不能伪造结果。不要只比平台曝光绝对值就判定内容优劣。

### 24h / 7d 与增量

- 发布约 24h / 7d 的累计快照，与两个快照之间的增量，是两种结果。
- 每天采集一次不能保证恰好覆盖发布后第 24 小时；必须返回实际观测时间及距目标时点的偏移。
- 没有历史快照、平台也不提供历史窗口时，不用“现在的总量”冒充过去 24h / 7d 的表现。
- 采样容差、补采与导出规则应在接入真实样本后确定；负增量需保留更正 / 删除等可能性并提示，不静默归零。

## 6. 交互与自动化边界

候选操作名只表达能力，不是已经存在的命令：

- `login`：打开专用可见浏览器，人完成扫码与验证。
- `sync`：在批准范围内读取平台、写入本地快照；这不是对外发布，但也不是完全无副作用的查询。
- `status`：显示登录态、同步状态、数据新鲜度和质量警告。
- `list` / `get` / `compare`：默认查本地数据，不隐式登录或抓取。
- `export`：显式生成导出文件，不自动覆盖消费者的台账。

MCP 的查询工具默认只读本地；联网刷新单独暴露并明确副作用，不把“查询数据”偷偷变成平台操作。接口返回缓存命中与采集时间，不能用过期数据伪装实时结果。

Web、CLI、MCP 共用同一查询与计算实现，统一返回 `schema_version`、来源、观测时间、缺失原因与警告。首版不内置 LLM，不要求模型 API Key；分析交给用户已有的 Agent。不暴露任意 SQL、任意 URL 抓取、通用浏览器控制或平台写操作。

同一个账号 profile 同时只允许一个登录 / 同步操作，其他调用返回明确的 busy 状态。长任务可返回 `sync_run_id` 供查询，不能阻塞看板读取旧快照。MCP 的 `readOnlyHint` 只是提示，不替代真实工具权限隔离。

登录过期、验证码、账号异常、权限拒绝或页面解析失败，均应返回明确的 `user_action_required` / 错误状态。不得自动密集重试、自动重新登录或自动切到另一账号。

同步频率待小样本实测后设定；原对话建议的“每天 1–2 次”只能作为保守试验候选，不是平台认可的安全阈值。并发、退避与定时任务须有上限，启用需用户确认。

## 7. 与下游内容台账的接入

首个消费者是作者私有仓库中的内容表现 CSV 台账与一个 CSV → JSON 脚本。现有脚本读取 CSV 并输出 JSON，不是采集器，也不是已经完成的数据看板。

候选对接方式：

1. Hub 独立提供带平台原生 ID、链接、时间与口径的 JSON / CSV。
2. 消费端维护平台原生 ID 到内容台账的映射；现有台账没有原生 ID、部分链接仍为“待补”，初次关联要人工核对，不能仅靠标题匹配后覆盖。
3. 只导入已验证的统计字段；`pillar`、`project`、候补名单、询单、审稿状态等业务字段仍由下游台账维护。
4. 缺失导出为空，不用“待补”塞入数字列，不把 `null` 变成 0。
5. `waitlist_7d` / `inquiries_7d` 不是通用平台互动指标，不由评论数或私信数猜测。
6. 是否自动写回台账是待决项；首版先显式导出，由消费者确认合并。

接入前还需核对现有消费者校验：当前台账含 `home-lab`，而脚本的 `PILLARS` 尚未包含它。本轮不修这个独立问题，也不把“导出成功”视为现有看板已兼容。

- `johenking/douyin-creator-cockpit` 为 MIT，但抓取依赖 macOS Chrome + AppleScript，不能直接解决 Windows 首版。
- `3441293738/creatorhub` 已是同名活跃项目；本轮所查完整代码树未找到许可文件。`wenyg/douyin-creator-tools` 同样未找到许可文件，不作为可直接复制分发的底座。发布前另选辨识度更高的名称。
- 当前 `MediaCrawler` 上游为非商业学习许可证，不作为 MIT Hub 默认采集依赖；已有本机可用能力也不等于获得再分发权。

## 9. 技术建议与许可证

推荐**本地模块化单体**，而不是把多个独立 MCP / 爬虫服务再拼成一层 Hub：

```text
两平台官方入口 / 专用浏览器
              ↓
平台 adapter → 校验 / 口径 / 同步记录 → SQLite 快照
                                             ↓
                                   共用查询与分析 module
                                      ↙      ↓      ↘
                                  本地 Web   CLI     MCP
```

- 语言组合候选：Python + FastAPI / SQLite / Playwright，前端采用预构建的 React + TypeScript 静态资源。理由是已找到的 MIT 小红书采集与看板实现均在此生态，具体复用范围和依赖仍待实现前确认。
- 最终用户运行本地 Python 应用与浏览器即可；Node 作为前端开发 / 构建依赖，不再要求常驻第二个前端服务器。不默认增加 Next.js、Electron / Tauri、Redis、数据库服务器或插件市场。
- 浏览器使用仓库外的专用 profile，不接管用户日常 Chrome 默认目录。优先 Playwright 直接管理；CDP 仅在实际需要接管 Hub 自己启动的专用浏览器时评估。
- 平台变化留在两个 adapter 的 seam，采集结果对外隐藏页面、登录与分页细节；不把一套假通用爬虫接口暴露给 UI / Agent。
- SQLite 保留原始口径与每次观测；数据查询不依赖浏览器在线。同步串行、有期限、有错误状态；先不引入独立分布式队列。
- 本地 HTTP 默认仅监听 loopback，校验 Host / Origin 并保护可触发登录、同步或修改关联的入口；“只在 localhost”不自动等于安全。
- 新仓库采用 MIT 方向；复用兼容代码保留版权与许可声明，不复制 AGPL 或无明确许可代码。代码许可证不授予平台访问权。

复查触发：MIT 候选适配成本高于最小实现、两平台实际登录路径不成立、需要远程常开 / 多账号 / 多用户，或本地发行安装摩擦无法接受时，重新比较语言组合、浏览器扩展与桌面封装，不预先堆叠这些方案。

## 10. 验收标准

| 场景 | 必须观察到的结果 |
| --- | --- |
| 一个平台、一篇本人内容 | 取得稳定原生 ID；至少 3 个后台实际可见指标与人工核对一致；记录字段、来源、统计口径与采集时间 |
| 两个平台 | 各自独立完成上述验证；不能拿一个平台的值补另一个的平台字段 |
| 再次同步 | 保存新的观测；同一次同步重试不会重复落库；可计算两个真实快照间的变化 |
| 缺失与 0 | 缺失为 `null` 且附原因，真实 0 保持 0；时长不进入完播率字段 |
| 24h / 7d | 返回实际观测时点与偏移；无对应证据时明确不可得，不回填伪历史 |
| 登录 / 页面异常 | 有可见错误与用户处理提示，停止平台访问；历史快照不丢失，缓存不伪装为新数据 |
| CLI / MCP | 查询得到同一份数据；查询不隐式触发同步；输出不包含认证材料 |
| 本地看板 | 两平台作品、详情、趋势、粉丝变化可见；与 CLI / MCP 同口径，错误与陈旧数据显式展示 |
| 跨平台比较 | 用户可关联 / 解除关联作品；并排展示平台口径与观测时间，不按标题静默合并、不伪造可比性 |
| 粉丝趋势 | 至少两个真实观测可展示净变化；无历史时明确不足，不推算平台未给出的新增 / 流失 |
| 并发与部分采集 | 同账号同时登录 / 同步不产生两个浏览器写同一 profile；部分失败保留成功项、覆盖与失败原因 |
| 消费端导出 | 内容映射明确，不覆盖人工业务字段；缺失数值留空；没有冒充台账中不存在的 ID |
| 安全边界 | 首版无对外写工具；凭据与浏览器 profile 不进 Git、日志、模型上下文或公开夹具 |
| 公开交付 | 独立仓库、MIT 与复用声明；合成 demo 无需登录即可展示产品，真实账号数据与私人工作区引用不进入公开包 |

Windows 实机验收是首轮必要证据；其他 OS 未测必须标为未验证。安装耗时与长期稳定性先测量，不写未经验证的承诺。
